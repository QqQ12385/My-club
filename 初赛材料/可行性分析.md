# 可行性分析（初赛提交项）

## 1. 技术可行性

| 环节 | 结论 | 依据 |
|------|------|------|
| 钉钉对接 | ✅ 已真实联调 | 企业内部应用 Stream 长连接：群内 @机器人 消息实时进系统、统一入口回复经 OpenAPI batchSend 真实回群（双向闭环已实测通过） |
| 飞书对接 | ✅ 已真实联调 | 企业自建应用 WebSocket 长连接：单聊/群@机器人 消息实时进系统，文字/图片/文件收发全通（早期 21001 因走回调 URL 模式，改长连接后解决） |
| 微信个人号 | ⚠️ 无API → RPA 兜底 | 题目补充明确允许 RPA；Power Automate Desktop 系统自带零成本；控制频率、只读优先、可随时停用 |
| 双通道降级 | ✅ 已实现 | 主通道失败自动切备用（已通过端到端自测） |
| AI 能力 | ✅ 可行 | DeepSeek API 已持有 Key；且有规则引擎兜底 |
| 闭环核心 | ✅ 已跑通 | 接收→归一→展示→回复→通道发送→状态回流，钉钉/飞书双向真实闭环端到端验证通过 |

> 说明：飞书自建应用早期因个人组织走「回调 URL」模式无公网 IP 报 21001，后改用
> WebSocket 长连接模式（`lark-oapi` ws.Client）成功接入，与钉钉 Stream 同为长连接、
> 免公网回调。最终三平台：钉钉（Stream 双向真实）+ 飞书（长连接双向真实）+ 微信（RPA 采集）。
> 钉钉/飞书选型优势：个人可自建组织、长连接无需公网回调、未认证服务商 Stream 不限量。

**主要难点与应对预案**：
- ~~平台事件订阅需公网回调~~ 已规避：钉钉 Stream 长连接无需公网 IP，直接建连；
- RPA 稳定性 → 只作微信通道主力、其余平台备用；故障注入演示真实失败原因与降级路径；
- 平台限流（429）→ 指数退避重试 + 备用通道降级。

## 2. 数据可行性

- 平台消息：钉钉官方 Stream 事件订阅（真实收）+ RPA 桌面采集（微信），自采自用，无需外部数据集；
- 演示数据：后端内置 9 条跨平台种子消息，断网也可演示完整闭环；
- 消息去重：平台消息按 msg_id、RPA 采集按「发送人+时间+内容」哈希，重放不产生重复。
