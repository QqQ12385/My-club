一、比赛概述
1.1 比赛背景与目标
在数字化办公与日常生活中，用户面临三类高频痛点：一是需在飞书、微信、钉钉等多个平台间频繁切换处理消息；二是个人账单分散于各类支付与银行应用，难以统一归集；三是求职简历制作繁琐、难以精准匹配岗位。本次大赛设置三个相互独立的赛题，分别对应上述痛点，要求学生运用软件开发、API 集成、OCR、NLP 与大模型等技术完成可独立部署的工程作品。
大赛重点考察三项能力：复杂业务闭环的抽象与设计能力、工程化落地与独立部署能力、技术文档的精准表达能力。鼓励学生合理使用 AI 服务提效，但须对所用方案负责并可复现。
1.2 比赛规则
组队规则　每队 1—3 人，不得超过 3 人。队员一经报名确认，不得随意变更。
选题方式　本次比赛共发布三个独立赛题。各队通过抽签决定开发哪一个赛题，不可自由选择，亦不可将多个赛题合并开发。
资源提供　比赛方不提供任何沙箱环境或测试账号。飞书、微信、钉钉等平台开发者账号、API 密钥及 OCR / NLP 服务账号，均由参赛队伍自行申请和组织。
AI 服务使用　允许使用任何 AI 服务（大语言模型、OCR、NLP 等）辅助开发与实现，但必须在文档中明确说明所用服务、调用方式与集成位置。
独立部署　系统必须提供完整部署方案（Docker 镜像 / 部署脚本等），可在比赛指定的纯净服务器环境中独立运行，不得依赖本地开发环境或不可复现配置。

二、赛题详情
以下三个赛题为相互独立选题，各队抽签选定其一进行开发。每个赛题均须形成完整业务闭环，不得仅实现孤立功能点。
赛题1/ A　多平台连接器与统一消息管理
核心痛点：多平台消息割裂、来回切换效率低下
背景　用户日常需在飞书、微信、钉钉等多个平台间切换处理消息与待办，信息分散、响应滞后。本赛题要求开发一个连接器系统，统一接入多个平台，实现消息的集中管理与发送。
功能需求
对接至少两个主流办公 / 社交平台（飞书、微信、钉钉等），通过官方开放 API 或 Webhook 实现。
提供统一入口（Web 或移动端），集中展示来自各平台的消息通知、待办事项等。
支持从统一入口向指定平台发送文本消息、文件等。
实现消息格式的统一转换与适配，将不同平台的消息体映射为内部标准格式。
业务闭环要求（核心）
系统必须形成“消息接收 → 统一展示 → 处理 → 发送反馈”的完整闭环。例如：用户在一个入口阅读来自钉钉的待办，可直接回复处理，回复内容自动转换为钉钉格式并发送，同时状态同步更新。不允许只做单向接收或简单消息转发，必须体现业务处理的闭环与状态回流。
赛题2/ B　多源账单导入与个人财务管理
核心痛点：账单分散于各应用，难以统一归集与分析
背景　个人账单分散在支付宝、微信支付、银行 App 等处，用户难以统一管理、掌握收支全貌。本赛题要求开发一个账单管理系统，支持多种导入方式，自动分类并生成月度报表。
功能需求
截图 OCR 识别：上传账单截图，通过 OCR 技术提取金额、时间、交易类型等信息。
文件导出导入：支持 CSV / Excel 等格式账单文件的上传与解析。
API 对接（可选加分项）：直接对接支付平台开放接口获取账单。
自动对收支进行分类（餐饮、交通、工资、购物等），支持用户手动调整。
按月生成收支报表，含饼图、柱状图等可视化，展示收入构成与支出趋势。
支持按时间、类别查询，数据加密存储。
业务闭环要求（核心）
系统必须形成“账单采集 → 智能解析 → 自动分类 → 报表分析 → 用户修正反馈”的闭环。例如：OCR 识别后允许用户修正分类错误，修正后的数据应反哺优化分类模型或规则；报表应能帮助用户发现消费问题，并支持导出或分享。不允许只做简单的数据导入与展示，必须体现数据驱动决策与持续优化的闭环。



赛题 3/C　自然语言对话式简历生成与精准投放
核心痛点：简历制作繁琐、难以精准匹配岗位
背景　求职简历制作耗时，且投递缺乏针对性。本赛题要求开发一个对话式简历生成系统，通过自然语言交互收集信息、自动生成简历，并实现精准投放。
功能需求
提供对话式交互界面，通过多轮对话引导用户输入教育经历、工作 / 实习经历、技能、项目经验等。
利用 NLP 或大模型技术解析用户输入，自动抽取并填充简历模板。
支持生成结构化简历，可导出为 PDF / Word 格式。
用户输入求职意向（岗位、地点、薪资等），系统从内置职位库或招聘平台 API 中匹配合适职位。
提供“一键投递”或投递建议（含匹配度分析、投递话术），并记录投递状态。
业务闭环要求（核心）
系统必须形成“对话收集 → 信息抽取 → 简历生成 → 职位匹配 → 投递反馈”的闭环。例如：简历生成后，用户可基于职位要求反向优化简历内容；投递状态（已读、面试邀请等）应主动提醒，并支持用户反馈结果以优化匹配算法。不允许只做静态简历生成，必须体现求职全流程的闭环。

赛题四/D（银行/小区信息采集与查询系统）完整描述

背景：用户在办理金融业务、选择居住地等场景下，需要全面了解周边银行网点和小区的详细信息。然而，这些数据分散在地图服务、房产网站、银行官网等多个渠道，且查询方式单一，难以进行综合分析和决策。本赛题要求设计并实现一个系统，能够自动抓取银行、小区等POI（兴趣点）信息，并提供地图式、列表式等多种查询方式，形成数据持续更新与用户交互的业务闭环。

功能需求：
数据抓取与更新（数据抓取不能违法）：
从公开的地图服务（如高德、百度地图API）、房产信息网站、银行官网等渠道抓取银行网点（名称、地址、经纬度、营业时间、服务类型、联系电话等）和小区（名称、地址、经纬度、建成年代、均价、物业费、周边配套等）信息。
支持定时自动抓取与手动触发抓取，具备增量更新与去重能力。
提供数据清洗功能，处理缺失值、格式不一致等问题。
数据存储与管理：
结构化存储抓取的数据，设计合理的数据库表结构（如银行表、小区表、地理位置表等）。
支持数据版本管理，记录每次更新的时间与来源。
多维度查询与展示：
地图式查询：在电子地图上标注银行和小区的位置，支持缩放、平移。用户可通过框选、点击等操作查看详细信息弹窗。支持图层切换（仅显示银行、仅显示小区或同时显示）。
列表式查询：以表格或卡片列表展示搜索结果，支持按区域、银行类型、小区价格范围、建成年代等条件筛选，支持排序和分页。
组合关联查询：支持查询特定小区周边的银行网点（如距离某小区1公里内的所有ATM），或查询某银行服务范围内的小区信息。
查询结果可展示统计图表（如某区域银行密度图、小区价格分布等）。
用户交互与反馈：
允许用户对数据进行纠错、补充（如某银行已关闭、小区信息有误），提交后进入审核队列或直接更新（根据设计）。
记录用户查询行为，用于优化抓取策略（如热门查询区域优先更新数据）。

业务闭环要求（核心）：
系统必须形成“数据抓取→清洗存储→多维度查询展示→用户反馈/纠错→触发重新抓取或更新”的完整闭环。例如：
用户通过地图发现某小区周边缺少银行网点，提交“新增银行”请求，系统可自动触发该区域的重新抓取或通知管理员核实；
系统根据用户查询热点，动态调整抓取频率和区域，确保数据时效性；
用户反馈的数据错误经审核后，立即更新至数据库，并同步反映在地图和列表展示中。
不允许只做静态的数据抓取与展示，必须体现数据持续更新、用户参与优化和查询驱动的数据运营闭环。

非功能需求：
系统架构清晰，模块化设计，便于扩展新的数据源或查询方式。
前端界面友好，地图交互流畅，列表加载快速。
数据抓取需遵守目标网站的robots协议及相关法律法规，避免高频请求影响目标服务。
必须提供独立部署方案（Docker镜像/脚本），确保可在指定服务器运行。

赛题一 A（多平台连接器与统一消息管理）RPA提示补充

在原功能需求或参考实现部分，增加以下技术提示：

【技术实现提示——RPA方式】​

除了通过官方开放API或Webhook对接平台外，参赛队伍也可以考虑采用RPA（机器人流程自动化）方式实现消息的采集与发送。例如，在Windows环境下使用Power Automate等工具，模拟鼠标键盘操作，自动完成以下动作：

自动登录各平台桌面端，拷贝消息内容并粘贴到本系统；
自动将本系统编写的消息拷贝粘贴到对应平台的输入框并发送；
自动导出和导入文件、截图等。

此方式尤其适用于那些未开放API、API权限申请困难或仅提供桌面端操作的平台，可作为连接器实现的有效补充或替代方案。但需注意RPA方式的稳定性、异常处理（如弹窗拦截）及反自动化策略，并在文档中说明其优缺点。

赛题二 B（多源账单导入与个人财务管理）RPA提示补充

在原功能需求或参考实现部分，增加以下技术提示：

【技术实现提示——RPA方式】​

在账单导入方式上，除了截图OCR识别、文件导出导入、API对接外，参赛队伍还可以考虑采用RPA（机器人流程自动化）方式。例如，使用Windows下的Power Automate等工具，自动操作鼠标键盘，实现：

自动打开支付宝、微信支付、银行APP等，导航至账单页面；
自动选择时间范围，点击“导出”按钮，将账单文件保存到指定位置；
自动将导出的CSV/Excel文件导入到本系统进行解析；
或直接拷贝账单列表中的数据，粘贴到本系统的输入框中。

这种方式可以解决部分平台无法提供API、导出功能受限或需要人工定期操作的问题，提高账单采集的自动化程度。但需在设计中考虑RPA脚本的兼容性、异常处理（如登录验证码、页面结构变化）及安全性，并在文档中明确说明。

4.3 决赛演示与答辩安排
决赛采用现场演示或线上演示方式，由参赛队自行选择。演示须实时在比赛指定服务器上运行系统，完整走通所选赛题的业务闭环，并回答评委针对架构、部署与闭环设计的提问。
演示红线　仅展示零散功能、现场无法在指定服务器独立启动系统，将严重影响“业务闭环完整性”与“独立部署能力”两项得分。

五、评分标准
总分 100 分。评分以业务闭环为主线，不按孤立功能点累加；初赛可行性分析与初步验证作为晋级依据，决赛按下列五个维度综合评定。

业务闭环完整性（核心维度）

核心功能实现质量
25 分
针对所选赛题，核心功能实现的稳定性、准确性与用户体验（15 分）；是否正确处理边界情况，如 API 限流、OCR 识别错误、对话意图失败等（10 分）。
系统架构与独立部署能力
20 分
系统架构清晰，模块划分合理，接口定义规范（8 分）；必须提供可用的独立部署方案，能在指定服务器顺利部署运行（7 分）；代码规范、有注释、无严重安全漏洞（5 分）。
文档精准度与质量
15 分
设计文档精、准，无冗余堆叠，重点突出（8 分）；含精确部署指南、核心接口定义与架构图（7 分）。若文档超过 15 页或含大量无关内容，本项最多得 5 分。
创新与 AI 应用
10 分
合理使用 AI 服务（NLP、OCR、大模型）提升业务闭环体验（5 分）；有创新设计，如自动触发、智能分类推荐、简历优化建议等（5 分）。
